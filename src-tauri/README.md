# Marklet — 구조와 설계 (Rust · Tauri)

Marklet 은 **Rust(Tauri) 앱**이다. 창 · 파일 · 인코딩 · 저장 · 감시 · 인쇄는 Rust 가 맡고, 화면은 두 길 중 하나로 그린다:
**읽기만 하는 문서는 WebView2 없이 끝까지 그리는 네이티브 뷰어**(Win32 + Direct2D + DirectWrite)가, 그 밖의 문서는 시스템의 **WebView2**(Edge 엔진)가 TypeScript 렌더러(`src/markdown/*` · `src/desktop/main.ts`)로 그린다.
사용자에게 보이는 설명은 저장소 루트의 [`README.md`](../README.md) 에 있고, 이 문서는 만든 사람을 위한 것이다.

| 문서 | 그리는 곳 | 처음 글자가 보이기까지 | 메모리(문서 하나) |
|---|---|---|---|
| **읽기만 하는 문서**(수식 · Mermaid · SVG · 800KB 초과 · 스크린 리더 켜짐이 아닌 것) | **네이티브 뷰어** — WebView2 를 만들지 않는다 | **129 ms** | **52 MB · 프로세스 1개** |
| 그 밖의 문서 · 편집 · 인쇄 · PDF | WebView2 가 렌더러로 그린다. 뜨는 동안 네이티브 **미리보기**가 먼저 그려 둔다 | 130 ms(미리보기) → 진짜 렌더 795 ms | 439 MB · 7개 |

(이 PC, 2026-10-08, 최종 빌드. 옛 Electron 1.0.12 는 같은 조건에서 498 ms · 345 MB · 4개였다 — 아래 "속도".)

거기에 마지막 창을 닫아도 웹 창을 잠시 살려 두는 **빠른 시작**(켜 두면 로그인 때부터 미리 띄워 두는 **미리 켜 두기**까지)이 얹혀 있다 — 웹 길의 속도를 위한 것이다.
뷰어가 못 하는 것이 필요해지면(`Ctrl+E` 편집 · `Ctrl+P` 인쇄 · `Ctrl+Shift+P` PDF, 수식이 든 문서로 이동) 같은 창이 미리보기가 되어 WebView2 창에 넘어간다.

> 네이티브 뷰어는 **같은 화면을 근사**한다(레이아웃은 렌더러와 ±1~3 px, 코드 색 · 링크 걸기 · 표 맞춤 등에 작은 차이가 있다 — "네이티브 뷰어의 차이"). KaTeX · Mermaid · DOMPurify 의 Rust 쪽
> 대응품이 없어서 그런 문서는 WebView2 로 간다. **접근성(UI Automation) 트리가 없어서** 스크린 리더가 켜져 있으면 쓰지 않는다. 끄는 길: 보기 메뉴 '빠른 보기' · `MARKLET_NATIVE=0`.
> 이전 판(Electron, 1.0.12 까지)은 저장소 이력에 있다: `git show 9ed077f:desktop/main.cjs` · `git ls-tree -r 9ed077f --name-only | grep ^desktop/`.

## 빌드

요구: Rust(MSVC) · Visual Studio Build Tools · Node.js 20.19+ · WebView2 런타임(Windows 11 에는 기본으로 있다).

```bash
npm install                                              # 렌더러 의존성 + Tauri CLI
npm run build                                            # 설치 파일 → src-tauri/target/release/bundle/nsis/ (4.08 MiB)
npm run build:exe                                        # 실행 파일만 → src-tauri/target/release/Marklet.exe (약 2분)
npm run test:rust                                        # Rust 단위 시험 72개(인코딩 · 링크 · 설정 · 마크다운 · 배치 · 고르기 · 찾기 · 코드 색 · 그림 · Run 항목)
npm test                                                 # 렌더러 단위 시험 478개 (vitest)
node scripts/check-native-windows.cjs                    # 네이티브 뷰어 창 수명 · 진짜 입력 점검 20개 (release 빌드 + px-probe 필요)
node scripts/check-tauri-windows.cjs                     # 웹 창 수명 점검 15개 (MARKLET_NATIVE=0 으로 고정)
npm run notices                                          # THIRD_PARTY_NOTICES.txt (npm 번들 + Rust 크레이트 `cargo metadata`)
npm run icons                                            # icons/txt.ico
npm run docs:images                                      # README 스크린샷 · 배너(docs/images/) — 실제 앱을 CDP 로 몰아 찍는다(scripts/capture-docs.cjs)
```

⚠ 빌드 전에 떠 있는 `Marklet.exe` 를 끝낼 것(`taskkill /F /IM Marklet.exe`) — 실행 중인 파일은 지우지 못해 빌드가 옛 것으로 남는다.

⚠ 프런트(`src-tauri/frontend/`)를 고쳤다면 `cargo build` 만으로는 안 들어간다 — 위 `npm run build`(= `tauri build`)로 빌드해야 `vite build` 가 먼저 돈다.

## 속도

> 아래 표의 'Electron 1.0.12' 는 이 앱이 옛 판(Electron)이던 때의 값으로, 같은 PC · 같은 문서 · 같은 도구로 쟀다. 그 판은 저장소에서 빠졌으므로(`git show 9ed077f`)
> 다시 잴 수는 없고, 기록으로 남긴다. `scripts/bench-*.cjs` 는 이제 이 앱(`tauri` 대상)만 잰다.

### 네이티브 뷰어: 읽기만 하는 문서는 WebView2 를 만들지 않는다

순수 Tauri(WebView2)는 Electron 을 못 이겼다(아래). 그래서 WebView2 를 **쓰지 않는** 길을 더했다 — 읽기만 하는 문서는 `preview/` 의 창이 파싱 · 배치 · 그리기 · 입력을 전부 하고,
WebView2 는 뜨지도 않는다. 400 ms 바닥이 없다.

측정(이 PC, 2026-10-08, 중앙값. 문서: 샘플에서 수식 · Mermaid 를 뺀 `sample-nomath.md`):

| 장면 | | Electron 1.0.12 | Tauri 네이티브 뷰어 |
|---|---|---|---|
| **① 처음 켤 때** | 창이 보임 | 421 ms | **86 ms** |
| | 글자 · 진짜 화면이 보임 | 498 ms | **129 ms** (3.9배) |
| **② 닫았다가 다시 열 때** | | ①과 같다(둘 다 닫으면 프로세스가 끝난다) | ①과 같다 |
| **③ 앱이 떠 있을 때 문서를 하나 더** | 창이 보임 | 177 ms(빈 창) | **50 ms** |
| | 글자 · 진짜 화면이 보임 | 330 ms | **52 ms** (6.3배) |
| 메모리(6초 뒤, 프로세스 트리 합계: 작업 집합 / 개인) | | 345 / 214 MB (4개) | **52 / 26 MB (1개)** |
| 700KB 문서 | 글자가 보임 | — | **131 ms** · 작업 집합 64 MB(첫 화면만 먼저 놓고 나머지는 틈틈이) |

- 재는 법: `node scripts/bench-pixels.cjs --doc <문서>` · `bench-second.cjs --doc` · `bench-memory.cjs --doc`(같은 문서, 첫 회 버림). 변형을 견줄 때는 `--env K=V` · `--label`.
- **레이아웃 정합**: 종합 시험 문서(제목 · 문단 · 목록 · 인용 · 표 · 코드 · 그림 · 각주)를 렌더러와 블록마다 맞대 보면(`scripts/preview-parity.cjs`, 웹 쪽은 `MARKLET_NATIVE=0`)
  ±1~3 px 안이다. 어긋남은 줄 위에 인라인 코드가 있을 때 줄이 0.5~0.7 px 높아지는 것이 쌓인 것이다.
- **수식 · Mermaid 가 든 문서는 이 길이 아니다.** 그런 문서는 아래 웹 길의 숫자(① 782 ms vs Electron 513 ms)를 따른다 — 처음 글자는 네이티브 미리보기가 113 ms 에 보여 주지만
  진짜 렌더는 WebView2 가 뜬 뒤다. `미리 켜 두기`를 켜면 162 ms.
- 한 문단이 아주 길 때: DirectWrite 의 한 글 덩어리 배치는 길이에 대해 급하게 느려진다(20만 자 7초, 52만 자 34초). 문단을 약 5천 자 조각으로 나눠 놓아(`Block::Piece`) 76만 자 문단 하나인
  문서도 첫 글자가 329 ms 에 뜬다. 코드 상자는 60만 바이트 · 한 줄 16만 바이트를 넘으면 WebView2 가 그린다(`Features::huge` — 이때는 미리보기도 두지 않는다).

### 왜 순수 Tauri 는 Electron 을 못 이기나

WebView2 는 **처음 켤 때** 브라우저 프로세스부터 올려야 한다. `WebviewWindowBuilder::build()` 한 번이 약 400 ms 다:
실행 +67 ms 에 `msedgewebview2.exe`(브라우저) → +217 GPU · 네트워크 서비스 → +246 스토리지 → +343 렌더러 → +440 ms 에 창 완성.
Electron 은 같은 단계가 한 프로세스 안에서 175 ms 만에 끝난다. 플래그(`--in-process-gpu` · `--disable-gpu` · `--no-sandbox` ·
`NetworkServiceInProcess` · `CalculateNativeWinOcclusion` …)는 이 구간을 줄이지 못했다. 그 뒤 렌더러가 문서를 그리는 데
(HTML · JS 60 ms → 첫 청크 렌더 → 첫 레이아웃 90 ms → 첫 프레임이 화면에 오르기까지) 270 ms 가 더 걸린다. 이 부분은 두 판이 같다.
**두 판의 차이는 거의 전부 이 440 ms 대 175 ms 다.** 앱이 이미 떠 있으면 새 창은 약 95 ms 면 된다(브라우저 프로세스가 살아 있어서).

그래서 세 가지를 했다.
1. **네이티브 미리보기** — WebView2 가 도는 동안 별도 스레드가 같은 문서의 첫 화면을 그린다. 글자가 보이는 시각을 앞당긴다.
2. **빠른 시작** — 마지막 창을 닫을 때 창을 닫지 않고 숨겨 둔다(웹뷰가 이미 떠 있다). 5분 안에 다음 문서가 오면 그 창이 부팅 없이 문서를 받는다.
   숨겨 두는 동안 렌더러가 표본 문서를 한 번 그려 본다(코드·수식·글꼴 조각을 올리고 코드를 데운다) — 이 덕에 진짜 렌더가 287 → 171 ms 가 되었다.
   기본으로 켜져 있고, 보기 메뉴에서 끈다(아래 "빠른 시작").
3. **미리 켜 두기**(직접 켠 사용자만, 기본 꺼짐) — 로그인할 때 창 없이 앱을 띄워 두 번째 것을 계속 유지한다. 처음 켤 때(①)도 ② 처럼 된다.
   대가는 로그인해 있는 내내 창 없는 프로세스가 남는 것이다(320 / 203 MB, 문서를 열면 숨겨 둔 창 하나가 더 준비된다).

### 웹 길의 측정 — 수식 · Mermaid 가 든 문서 (이 PC, 2026-10-08, `docs/sample/주문서비스_개편제안서.md`, 중앙값, 문서를 연 순간 = 0)

| | 글자가 보임 | 510 ms | **48 ms** | |
| | 진짜 렌더가 보임 | 510 ms | **171 ms** | |
| **③ 앱이 떠 있을 때 문서를 하나 더 열 때** | 창이 보임 | 170 ms(빈 창) | **47 ms** | **48 ms** |
| | 글자가 보임 | 358 ms | **47 ms** | **48 ms** |
| | 진짜 렌더가 보임 | 358 ms | 418 ms | **166 ms** |

| 닫고 숨겨 둔 동안 | | — | 320 / 203 MB (7개) | |

- **글자가 보이기까지는 모든 장면에서 빠르다**: ① 4.5배 · ② 10배 · ③ 7.6배(미리 켜 두기를 켜면 ① 10배 · ③ 7.5배). 창이 보이는 것은 ① 6.4배 · ② 9배.
- **진짜 렌더(WebView2 가 그린 화면)는 기본 설정에서 ②에서만 앞선다**(171 vs 510 ms). ①에서는 782 vs 513, ③에서는 418 vs 358 로 Electron 이 빠르다.
  미리 켜 두기를 켜면 세 장면 모두 앞선다(162 · 171 · 166 ms vs 513 · 510 · 358 ms).
  (Tauri 쪽 값은 미리보기가 걷히는 시각이다 — 진짜 창은 그보다 50 ms 쯤 일찍 올라가 있고, 그 틈은 빈 프레임이 비치지 않게 일부러 둔 것이다.
  미리보기를 끈 쪽의 ① 은 697 ms.) 미리보기가 떠 있는 동안에는 스크롤만 된다(글자 선택 · 링크 · 찾기 · 목차 · 편집은 진짜 창이 뜬 뒤부터).
  그 사이에 그것들을 쓰려는 사용자에게는 이 판이 더 느리다.
- 미리보기를 끄면(`MARKLET_NO_PREVIEW=1`) ① 은 Electron 보다 약 190 ms **느리다**(697 vs 513).
- **왜 숨겨 둔 창이 이렇게 빠른가**: 새로 뜬 페이지의 첫 문서는 마크다운 해석기 · KaTeX · 코드 색 조각을 처음 올리고, 글꼴을 처음 찾고, 코드를 처음 돌린다 —
  진짜 렌더 시간의 상당 부분(125 ms 쯤)이 이것이다. 숨겨 둔 창은 그 값을 이미 치렀다.
- **메모리는 좋아지지 않았다.** 작업 집합은 오히려 늘었고 개인 메모리만 조금 줄었다. 숨겨 둔 동안에는 창이 열려 있을 때보다 100 MB 쯤 적다
  (`set_memory_low`). 웹뷰를 재우는 `TrySuspend` 는 개인 메모리 27 MB 만 줄여서 넣지 않았다.
- 반복 측정에서 앞 두 자리가 흔들린다(PC 상태에 따라 한 번에 ±50 ms). 값은 8~15회 중앙값이다.
- 이 표는 네이티브 뷰어를 넣기 전 빌드로 쟀다. 마지막 빌드에서 ① 의 기본 열만 다시 쟀다(`MARKLET_NATIVE=0`, 9회): Electron 창 435 · 글자 509 · 진짜 렌더 509 ms,
  Tauri 창 93 · 글자 130 · 진짜 렌더 795 ms — 같은 범위다(미리보기 글자가 113 → 130 ms 로 늘었다. 창을 만드는 공통 경로가 이 사이에 커진 것인데 원인은 가르지 않았다).

### 어떻게 쟀나 (그리고 속은 곳)

`node scripts/bench-pixels.cjs [--runs N]` + `scripts/px-probe`(Rust). 앱을 띄우는 순간부터 창을 `PrintWindow` 로 계속 떠서
**글자의 가장자리**(가로로 이웃한 픽셀의 밝기가 크게 바뀌는 곳)가 4000 개를 넘는 첫 시각을 잰다. 변형을 번갈아 돌리고 첫 회는 버린다.
`bench-second.cjs`(앱이 떠 있을 때 둘째 문서) · `bench-warm.cjs`(창을 닫았다가 다시 열기) · `bench-memory.cjs`(프로세스 트리 합계) · `bench-startup.cjs`(렌더러 DOM 기준, CDP) ·
`trace-startup.cjs`(Rust 쪽 구간 표지) · `preview-parity.cjs`(미리보기 배치 ↔ 렌더러 블록 위치) · `check-tauri-windows.cjs`(창 수명 시나리오).

속은 곳 — 같은 실수를 하지 마라:
1. **짙은 픽셀 수로 글자를 세면 속는다.** 아직 안 그려진 WebView2 창은 `PrintWindow` 에서 *검게* 나오고, 그게 '글자'로 세어졌다.
   그래서 미리보기 없는 Tauri 판이 Electron 과 같다고(≈520 ms) 한동안 적었는데 실제로는 ≈700 ms 였다. 가장자리 수로 바꿨다.
2. **임계값이 낮으면(1500) '파일을 끌어다 놓으세요' 안내 화면이 글자로 세어진다**(1785). 샘플 문서의 진짜 글자는 9000~14000 이다.
3. **DOM 기준(`bench-startup.cjs`)은 Electron 을 낮게 잰다**(h1 이 DOM 에 생긴 시각 319 ms, 화면에 보인 시각 520 ms).
4. **화면 캡처 모드(`PX_SCREEN=1`)는 창 뒤에 글자가 있으면 그것이 비친다**(Windows 가 창을 페이드 인 하는 동안 뒤의 앱이 보인다).
   그래서 판 사이 시각 비교에는 쓰지 않고, 미리보기 → 진짜 창이 바뀔 때 **빈 프레임이 비치는지**(`gaps`)를 볼 때만 쓴다.
5. `trace-startup.cjs` 처럼 Node 에서 띄워 재면 Node 의 프로세스 생성 지연(≈25 ms)이 얹힌다. 견주는 값은 같은 도구(`px-probe`)로만 잰다.

## 네이티브 뷰어 (`src-tauri/src/preview/` · `native.rs`)

같은 창 코드가 두 가지로 쓰인다. **뷰어**는 문서를 끝까지 보여 주고(WebView2 없음), **미리보기**는 WebView2 가 뜨는 동안만 있다가 걷힌다.
창이 문서를 읽고 모양을 정한다(`Handle::wait_mode`): 네이티브로 끝까지 그릴 수 있으면 뷰어, 아니면 미리보기 — 앱은 그 답을 기다렸다가 뷰어면 WebView2 창을 만들지 않고, 미리보기면 만든다.

### 구성

| `layout.rs` | 블록 → 그릴 것(글 · 상자 · 선 · 그림). DirectWrite. 수치는 렌더러가 실제로 계산한 값. 글마다 UTF-16 원문 · 링크 구간 · 읽는 순서 번호(`TextMeta`)를 든다 |
| `hl.rs` | 코드 색 — highlight.js 가 칠하는 열두 언어(js · ts · python · java · kotlin · bash · json · yaml · xml/html · sql · css · markdown)를 근사하는 토크나이저 |

| `view.rs` · `paint.rs` | 창을 모르는 상태(배치 진행 · 스크롤 · 목차 · 찾기)와 Direct2D 그리기(고른 글 · 찾은 글 · 도크 · 찾기 막대 · 떠오르는 컨트롤 · 스크롤바) |

### 하는 것

글자 고르기(드래그 · 더블클릭 낱말 · 트리플클릭 문단 · Ctrl+A) · 복사(Ctrl+C, 표는 탭 · 줄바꿈) · 링크(바깥 주소는 기본 브라우저, `#앵커` · 각주는 문서 안 이동, 상대 `.md` 는 같은 창에 열기) ·
찾기(Ctrl+F, 한글 초성 · 개수 · 다음/이전) · 목차 도크(Ctrl+T, 읽는 절 따라가기) · 원문 보기(Ctrl+U, `.txt` 는 원문이 기본) · 확대(Ctrl+휠 · Ctrl+±/0) · 테마(설정 · 시스템 따라가기) ·
로컬 그림(둥근 모서리, 링크 감싼 그림) · 코드 가로 스크롤(Shift+휠) · 앞머리 접기/펴기 · 떠오르는 컨트롤(마우스를 움직이면 나타남, 툴팁) · Alt 메뉴 막대 · 우클릭 메뉴 · F11 전체 화면 ·
끌어다 놓기 · 외부 변경 자동 갱신(읽던 자리 유지) · 창 크기 · 자리 저장(저장된 자리가 어느 모니터에도 안 걸치면 기본 자리).

### WebView2 로 넘어가는 것

- 문서에 **수식**(`$…$` · `$$` · `\(…\)` · `\[…\]` · ` ```math `) · **Mermaid** · **SVG 그림**이 있다. **원격 그림**은 '원격 이미지 불러오기'가 켜져 있을 때(꺼져 있으면 렌더러처럼 자리표시자).
- 문서가 800KB 를 넘는다(`NATIVE_MAX_BYTES` — 문서 전체를 메모리에 놓는다). 코드 60만 바이트 · 한 줄 16만 바이트 이상의 덩어리가 있다.
- **스크린 리더가 켜져 있다**(`SPI_GETSCREENREADER`). 네이티브로 그린 글에는 접근성 트리가 없다. 열린 뒤에 켜지면(`WM_SETTINGCHANGE`) 그 창을 웹 창으로 넘긴다.
- 사용자가 편집(Ctrl+E) · 인쇄(Ctrl+P) · PDF(Ctrl+Shift+P)를 누르거나 뷰어에서 연 링크가 수식 문서다 — 같은 창이 미리보기가 되어 WebView2 창을 만들고(`native::upgrade`),
  그 창이 그리면 걷힌다. 누른 일은 그린 뒤에 한다. 설정 `nativeView` 를 끄거나 `MARKLET_NATIVE=0` 이면 전부 웹 길이다.

### 네이티브 뷰어의 차이 (알고 있는 것)

- 표가 화면보다 넓으면 렌더러(fit-width)처럼 글자를 줄이되(바닥 0.55) 그래도 안 들어가면 **낱말 안에서 줄을 바꾼다**(렌더러는 가로 스크롤).
- 맨 주소 자동 링크는 `http(s)://` · `www.` · 메일 주소만 건다 — markdown-it(linkify-it)이 걸어 버리는 `README.md` 같은 '도메인처럼 보이는 글'은 걸지 않는다.
  허용 목록 밖 주소(`javascript:` · `C:\x` · `//host`)의 링크는 글자만 남는다(렌더러는 `[x](…)` 원문을 그대로 보인다).
- 목차에는 제목의 글자만 적는다(렌더러는 제목의 마크다운 원문을 적는다). 코드 색은 자체 토크나이저의 근사라 드문 꼴(정규식 리터럴 · 중첩 보간)에서 다를 수 있다.
- 우클릭 메뉴 · 메뉴 막대는 Windows 기본 메뉴다(렌더러는 앱이 그린 둥근 메뉴). 다크 테마에서는 uxtheme 의 비공개 호출로 어둡게 한다(없는 Windows 에서는 밝게 남는다).
- 글 선택은 마우스로만(Shift+클릭 · Shift+방향키로 늘리기 없음). 코드 가로 스크롤바는 휠로만 움직인다(끌기 없음). 터치 제스처 없음. Tab 은 아무것도 안 한다(렌더러와 같다).
- 인라인 코드가 든 줄은 렌더러보다 0.5~0.7 px 낮다(쌓이면 긴 문서 끝에서 2~3 px).

### 미리보기

WebView2 를 써야 하는 문서의 첫 화면을 먼저 그린다. 같은 코드가 그리지만 입력은 스크롤(휠 · PageUp/Down · Home/End · 방향키)만 받는다.

- **창마다 하나.** 첫 문서는 프로세스가 켜지자마자(Tauri 보다 먼저, `main()` 첫머리) 띄우고, 앱이 떠 있는 동안 여는 문서는 창을 만들 때 띄운다.
  이미 떠 있는 앱이 있으면(`<identifier>-sim` 뮤텍스) 첫 문서 미리보기를 띄우지 않는다 — 그 프로세스는 문서를 넘기고 곧 끝난다.
- **스레드**: 미리보기 스레드(창 · Direct2D · 메시지 루프) + 준비 스레드(DirectWrite 공장 · 글꼴 · 마크다운 파싱 — 창 만드는 동안 병행).
  Direct2D 렌더 타깃은 **소프트웨어**로 만든다(하드웨어 가능 기본값은 D3D 장치 때문에 165 ms, 소프트웨어는 26 ms).
  `HwndRenderTarget` 대신 `DCRenderTarget` 도 시험했는데 만드는 값이 같고 `ShowWindow` 가 더 느려서 되돌렸다.
- **배치**: `md.rs`(pulldown-cmark → 블록 트리) → `layout.rs`(DirectWrite 로 글을 놓는다). 수치는 렌더러가 **실제로 계산한 값**을 옮긴 것이다
  (본문 17px · 줄 높이 1.75 · 제목 1.7/1.4/1.2/1.05em · 표 · 코드 상자 · 인용 · 목록 · 각주 …). 여백은 CSS 의 margin collapse 를 흉내 낸다.
  글꼴은 렌더러의 글꼴 목록 순서를 따른다(본문 Segoe UI → 한글은 Noto Sans KR → 시스템, 코드는 Roboto Mono → DejaVu Sans Mono → Consolas).
  한글 어절은 `word-break: keep-all` 처럼 U+2060 으로 이어 놓는다.
  **큰 문서**는 첫 화면(+600px)까지만 먼저 놓고 나머지는 타이머로 6 ms 씩 이어 놓는다(131 KB 문서도 처음 글자는 같은 시각에 뜬다).
  원문은 20만 자까지만 읽는다.
- **넘기기**: 진짜 창(`visible(false)`로 만든다)은 `ready` 때 미리보기 **바로 뒤**에 보여 둔다(`SetWindowPos`, 활성화 없이). 렌더러가 첫 블록을 그리고
  그 프레임이 화면에 올랐다는 알림(Element Timing)까지 받으면 `painted` 를 보내고, Rust 가 미리보기를 걷는다. 4초 안에 안 오면 어쨌든 넘긴다.
  어느 문서의 첫 화면을 알려야 하는지는 Rust 가 정해 문서와 함께 보낸다(`announce`) — 렌더러가 '처음 받은 문서'로 짐작하지 않는다(숨겨 둔 창은 표본 문서를 먼저 받는다).
  - rAF 두 번만 믿고 걷으면 **아직 안 올라간 빈 프레임이 잠깐 비쳤다**(화면 캡처로 8회 중 2~4회). 올라갔다는 알림까지 기다리면 34회 중 1회,
    거기에 걷는 것을 50 ms 늦추면(`PREVIEW_LINGER` — DWM 이 합성할 틈) 30회 중 0회.
  - 미리보기에서 이미 내려 읽고 있었다면(`scroll_y`) 렌더러가 그 자리로 간 뒤 `swap` 으로 넘긴다.
  - DWM 페이드 인/아웃은 두 창 모두 끈다(`DWMWA_TRANSITIONS_FORCEDISABLED`) — 안 끄면 미리보기가 사라진 뒤 진짜 창이 반투명한 채로 드러난다.
  - 진짜 창이 먼저 떠서 미리보기가 아직 안 떴으면 미리보기는 뜨지 않고 접는다(`cancelled`) — 뒤늦게 떠서 진짜 창을 덮는 유령 창이 되면 안 된다.
  - 진짜 창이 뜨기 전에 사용자가 미리보기를 닫으면: 첫 창이면 앱 종료, 그 밖의 창이면 그 문서의 창만 닫힌다(`close_requested`).
- 문서를 여는 모든 창(미리보기가 없는 것 포함)은 **문서가 그려진 뒤에 보인다**(`show_pending`). 그 전에 보이면 '파일을 끌어다 놓으세요' 안내가 잠깐 비친다.
- 미리보기가 **하지 않는** 것: 수식은 자리만 잡고 원문을 놓고 Mermaid 는 코드 상자로 둔다. 입력은 스크롤만 받는다 — 글자 선택 · 링크 · 찾기 · 목차 · 편집은 진짜 창이 뜬 뒤부터
  (그 사이에 그것들을 쓰려는 사용자에게는 웹 길이 더 느리다). 블록 높이는 렌더러와 ±0.6 px 안에서 맞는다. 수식 · 위첨자가 든 문단은 +2.3 px 보정으로 맞춘다.
- 덩어리가 너무 큰 문서(`Features::huge`)는 미리보기도 두지 않는다 — 첫 화면을 놓는 데 몇 초가 걸린다.
- 연구용 스위치(환경변수): `MARKLET_NO_PREVIEW=1`(끔) · `MARKLET_PREVIEW_HOLD=1`(걷지 않음) · `MARKLET_PREVIEW_SCROLL=<px>`(내려 둔 채 시작) ·
  `MARKLET_PREVIEW_DUMP=<파일>`(블록 위치 덤프) · `MARKLET_TRACE=<파일>`(시각 기록) · `MARKLET_NATIVE=0`(네이티브 뷰어 끔) ·
  `MARKLET_DATA_DIR=<폴더>`(설정 폴더를 돌린다 — 점검 · 측정 스크립트가 `scripts/lib/profile.cjs` 로 쓴다. 웹뷰 데이터는 `WEBVIEW2_USER_DATA_FOLDER`). 렌더러와 위치를 맞대는 것은 `scripts/preview-parity.cjs` 가 한다.

## 빠른 시작 (닫은 뒤에도 잠시 살려 두기)

- **무엇을**: 마지막 창을 닫으면(저장 확인을 거친 뒤) 창을 닫지 않고 숨긴다(`app.rs` `go_warm`). 렌더러는 `reset` 명령으로 맨 처음 모습이 되고
  (편집 · 찾기 · 목차 · 확대 보기를 다 닫는다), 문서 상태 · 파일 감시는 치운다. 전체 화면 · 최대화 · 메뉴 막대도 되돌린다.
  다음 문서가 오면 그 창이 부팅 없이 받는다(`reuse_warm`) — 미리보기도 다시 뜬다. 5분 안에 안 오면 앱이 끝난다(`MARKLET_WARM_SECONDS` 로 시험).
- **끄기 · 끝내기**: 보기 메뉴의 '닫은 뒤에도 잠시 준비해 두기'(설정 `keepWarm`, 기본 켬). 파일 메뉴의 '끝내기'(Ctrl+Q)는 숨기지 않고 끝낸다.
  끈 채로 닫으면 예전처럼 앱이 바로 끝난다. 같은 창을 20번 쓰면 새 창으로 바꾼다.
- **보이지 않는 프로세스가 남는다**: 닫은 뒤 최대 5분 동안 창 없는 `Marklet.exe` 와 WebView2 프로세스가 남는다(320 / 203 MB). 작업 관리자에 보인다.
  설치기가 그것 때문에 '실행 중입니다' 를 물어보지 않게 `installer-hooks.nsh` 가 설치 · 제거 전에 `Marklet.exe --quit-warm` 을 먼저 보낸다
  (창이 떠 있으면 아무것도 안 하고, 숨겨 둔 채 기다리는 중이면 끝낸다). **이 훅은 설치기를 실행해 보지 못해 검증하지 못했다.**
- **죽은 창 복구**: 숨겨 두는 동안 렌더러가 죽었을 수 있다. 문서를 보냈는데 1.5초 안에 렌더러가 `received` 를 안 보내면 새 창을 만들고 그 창을 버린다
  (렌더러를 강제 종료해 시험했다: 문서는 1.8초 만에 뜬다). 느리게 그리는 것은 죽은 것이 아니므로 보지 않는다.
- **왜 FCP 가 아니라 Element Timing 인가**: 미리보기를 걷는 신호로 쓰던 `first-contentful-paint` 는 페이지가 처음 뜰 때 한 번뿐이다. 다시 쓰는 창에서는
  이미 지난 값이라 아무것도 기다리지 못한다. 첫 블록들에 문서마다 다른 이름의 `elementtiming` 을 달아 그 프레임이 화면에 올랐다는 알림을 받는다.
- **미리 켜 두기**(보기 메뉴, 기본 꺼짐): 켜면 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 에 `"<exe>" --background` 를 쓴다(`autostart.rs` — 이 값 하나만 쓰고 지운다).
  로그인 20초 뒤 창 없이 부팅해 숨겨 둔 창이 되고(대기 시간 없이 계속 남는다), 숨겨 둔 창을 쓰고 나면 곧 다음 것을 하나 더 만들어 둔다(`ensure_spare`).
  창이 안 보이는 프로세스가 로그인 내내 남고 숨겨 둔 창 하나가 개인 메모리 +166 MB 쯤 든다 — 그래서 직접 켠 사람만 치른다. 닫은 뒤에 잠깐 기다리는 빠른 시작은 이 여분을 만들지 않는다.
  끝내기(Ctrl+Q) · `--quit-warm` 으로 끝난다(다음 로그인에 다시 뜬다). 제거하면 훅이 Run 값을 지운다. 시험은 진짜 Run 키를 건드리지 않는다(`MARKLET_RUN_KEY`).
  **켜 둔 채로는 `cargo build` 가 실행 파일을 덮어쓰지 못한다**(떠 있는 파일이다) — `Marklet.exe --quit-warm` 을 먼저 보낸다.
- 아직 안 한 것: 창이 열려 있는 동안 여분 창을 만들어 두기(③ 의 진짜 렌더가 418 → 176 ms 가 되지만 창이 둘 이상인 내내 개인 메모리 +166 MB 가 든다 — 값이 너무 크다고 보고 뺐다).

## 창을 여럿 열 때

창을 **한꺼번에** 만들면 둘째부터 웹뷰가 망가진다 — Tauri 가 주입하는 `__TAURI__` 가 안 들어가거나 IPC 가 영영 답을 못 받는다
(문서 셋을 동시에 열면 둘은 되고 셋부터 안 됐다. 미리보기와 무관하게 재현). 그래서 `app.rs` 의 `BOOT` 가 앞 창이 `ready` 를 알린 뒤
250 ms 가 지나야 다음 창을 만든다(0 ms 에서 실패, 100 ms 에서 5창 × 3회 성공). `setup` 안에서는 첫 창만 만들고 나머지는 이벤트 루프가 돈 뒤에 연다.
탐색기에서 문서 여러 개를 골라 열 때가 이 길이다. 원인(wry/WebView2 쪽)은 못 찾았다.

## 네트워크 (문서를 여는 동안 외부 요청 0건이 목표다)

WebView2 는 가만히 두면 시작 직후 Edge 설정 서비스(`config.edge.skype.com`)와 보안 DNS 확인(`dns.google`)을 부른다.
`webview.rs` 의 `BROWSER_ARGS` 로 백그라운드 네트워킹을 끄고 두 주소를 이름 해석 단계에서 막았다.
net-log 로 시작~종료를 기록해 보면(2026-10-08, 최종 빌드, 수식 문서) 문서 내용이 담긴 요청은 0건이고, Windows 프록시 자동 감지용 `wpad` 조회와
막힌 `dns.google` 시도(`~NOTFOUND`, 같은 요청 8번)만 남는다. 편집기에서 틀린 글을 쳐 맞춤법 검사를 일으켜도 새 요청은 없다. **시스템 DNS 가 구글이면 이 시도가 생기는 구조이고, 이름 해석 규칙으로만 막은 것이다.**
네이티브 뷰어는 문서를 연 6초 동안 TCP 연결 0 · UDP 끝점 0 · 자식 프로세스 0 이었다.

확인하는 법(net-log):

```powershell
$env:MARKLET_NATIVE = '0'
$env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS = '--log-net-log=C:\temp\net.json'
.\Marklet.exe 문서.md      # 닫고 나면 net.json 에 요청이 남는다
```

## 알려진 차이

- 인쇄 미리보기는 WebView2 의 Edge 인쇄 창이다(머리글/바닥글 기본 켜짐, 'PDF 로 저장' 기본 이름 = 문서 제목).
  옛 Electron 판의 '내장 PDF 뷰어 + 밝은 테마 고정' 미리보기와 모양이 다르다.
- 로컬 그림 주소는 `window.marklet` 설치 때 `setAttribute` 를 감싸 `marklet-local://` → `http://marklet-local.localhost/` 로
  바꾼다(`local-image.ts` 를 건드리지 않으려고). `local-image.ts` 가 브리지에서 주소를 받게 고치는 편이 낫다(미룬 일).
- 설정 폴더: `%APPDATA%\com.marklet.md.desktop\state.json`. 처음에 한해 옛 Electron 판의 `%APPDATA%\marklet\state.json` 을 이어받는다.
- WebView2 런타임이 없는 PC 는 설치기가 부트스트래퍼를 내려받는다(인터넷이 필요).
- 실행 파일이 6.07 → 10.2 MB(9.71 MiB)로 늘었다(네이티브 뷰어의 Direct2D · DirectWrite · WIC 바인딩 · pulldown-cmark · `panic = "unwind"`). 설치 파일은 3.39 → 4.08 MiB.
- **옛 Electron 판(1.0.12 이하)과 나란히 깔면 서로 덮어쓴다.** 설치 위치(`%LOCALAPPDATA%\Marklet` ↔ `\Programs\Marklet`)와 제거 항목이 따로 생기고,
  같은 `Marklet.Markdown` 연결 · `Applications\Marklet.exe` 를 마지막에 설치한 쪽이 차지한다. 설치기의 PREINSTALL 훅에서
  Electron 판의 제거 프로그램을 조용히 돌려 이어받게 해야 한다(아직 안 했다 — README · 릴리즈 노트는 '예전 판부터 제거하라'고 안내한다).
  나중에 예전 판을 지우면 그 제거 프로그램이 `Applications\Marklet.exe` · `Marklet.Text` · `RegisteredApplications` 값을 같이 지워 새 판의 연결이 풀린다.

## 해 보고 접은 것 / 안 해 본 것

- 해 보고 접음: 첫 화면을 Rust 가 HTML 로 만들어 WebView2 에 미리 꽂기(SSR) — 진짜 렌더가 보이는 시각이 −67 ms 뿐이었다 ·
  첫 청크를 40 토큰으로 줄이기 − 30 ms 쯤(렌더러는 두 길이 같이 쓴다) · 진짜 창을 숨겨 두었다가 `show()`
  대신 미리보기 뒤에 미리 보이기 — 시각은 같고, 빈 프레임이 비치는 것만 `first-contentful-paint` 를 기다려야 막혔다 ·
  `DCRenderTarget` · 렌더 타깃 만들기를 다른 스레드로 미루기(창 · 렌더 타깃 · 보이기가 서로 물려 있다).
- 해 봄: **WebView2 를 아예 쓰지 않는 네이티브 뷰어**(위) — 읽기만 하는 문서의 400 ms 바닥을 없앴다. 대가는 렌더러와 같은 화면을 **근사**한다는 것(차이 목록)과 접근성 트리가 없다는 것이다.
- 안 해 봄: 네이티브 뷰어의 UI Automation 제공자(스크린 리더가 글을 읽게 — 지금은 스크린 리더가 켜지면 웹으로 간다) · 수식(KaTeX) · Mermaid 의 네이티브 그리기(대응품이 없다) ·
  원격 그림 불러오기(WinHTTP 로 하면 된다 — 지금은 웹으로 간다) · 편집기(IME 를 직접 다뤄야 한다 — 웹으로 간다) ·
  WebView2 환경을 `main` 첫머리에서 미리 만들기(약 −20 ms) · `--single-process`(지원되지 않는다).
